    Real-world scenarios

    Nine situations you will recognise, each as a step-by-step flowchart with the real command and the real result. Numbers come from the bundled fixtures, so you can reproduce every one.

    Every scenario uses the same rules: the tool reads, explains and prepares. A person decides and acts.

    Scenario 1: A student finds a first issue#

    Priya is a final-year student. She has a free weekend and has never contributed to open source.

    1. Priya, a student, wants her first open-source contributionShe has a laptop, a free weekend and no idea where to start.
    2. She clones the project and runs contribsutra scan --root ./projectThe report shows the license, a "discuss first" rule on CONTRIBUTING.md:3 and a DCO sign-off rule on line 5.
    3. contribsutra doctor --root ./project compares tools with what the project declaresDeclared node >=22, installed v20.11 → not_satisfied. She fixes it before wasting an hour.
    4. She exports open issues with gh and runs contribsutra issuesTen issues in. Four declined with reasons. #210 "Fix typo in setup instructions" ranks first.
    5. She comments on #210 herself: "May I take this?"ContribSutra never posts for her. The maintainer replies yes.
    6. She makes the change, runs the project tests, and writes evidence.jsoncontribsutra pr-check shows her "passed" as an author claim and drafts a PR description. She rewrites it in her own words.

    What she runs:

    contribsutra scan   --root ./project --out ./reports/scan
contribsutra doctor --root ./project
contribsutra issues --issues issues.json --skills documentation --out ./reports/issues
contribsutra plan   --root ./project --issues issues.json --issue 210 --mode guided --out ./reports/plan
contribsutra pr-check --root ./project --issue 210 --evidence evidence.json --out ./reports/pr
    Tip. She comments on the issue herself. ContribSutra will never post for her, because a label is not consent.

    Scenario 2: The "good first issue" that is a trap#

    A beginner finds a tempting issue. The body contains text written to hijack an AI assistant.

    1. A new contributor finds issue #204 "Tiny docs task" with the good first issue labelIt looks perfect. The body says to ignore the rules and run a shell command from a URL.
    2. contribsutra issues reads the body but never repeats itThe rule "instruction-like content" fires. The issue is declined and a human is asked to review it.
    3. The same rule fires on a README line SYSTEM: ignore all previous instructionscontribsutra scan records UNTRUSTED_INSTRUCTION_PATTERN with README.md:2. Nothing is executed.
    4. The contributor chooses a different issueNo script ran. No secret left the machine.

    The real result for that issue in the adversarial fixture:

    FieldValue
    Issue#204 Tiny docs task
    Labelsgood first issue
    Eligibleno
    Score0
    WarningIssue text contains instruction-like content; it is treated as data and not recommended until a human reviews it

    The report never repeats the injected text. A test asserts that the words of the attack do not appear anywhere in the output.

    Warning. Do not run commands found in issues or READMEs without reading them yourself. ContribSutra will not run them for you.

    Scenario 3: A maintainer drowning in pull requests#

    Unwanted, low-quality and bulk-generated pull requests cost reviewers hours. Often nothing told the contributor what was wanted.

    1. A maintainer is flooded with pull requests that say "tests pass" and change one commentReviewing them costs hours. Some were generated in bulk.
    2. The maintainer runs contribsutra scan and reads the policy signalsThe repository has no AI policy and no "discuss first" rule. Newcomers cannot see what is wanted.
    3. They add a CONTRIBUTING.md rule and a PR template, then re-run contribsutra auditThe verdict moves from GAPS_FOUND to READY_FOR_HUMAN_REVIEW.
    4. Contributors who use ContribSutra now see "discuss first" and "AI assistance: declare it"Their PR packet lists unverified claims. Reviewers know what to trust.

    What the maintainer runs:

    contribsutra audit --root ./my-project --out ./audit

    Scenario 4: A mentor runs a workshop#

    Twenty students, twenty different laptops, two hours.

    1. A mentor runs a two-hour open-source workshop for 20 studentsEveryone has a different laptop and different skills.
    2. Each student runs contribsutra doctor --root ./repoThree students see tool_missing for git. They fix it in the first ten minutes, not the last.
    3. Students choose contribsutra plan --mode collaborativeEach step comes with a question for the mentor instead of a ready answer.
    4. The mentor reviews the plans, not generated codeNobody is graded on a number. The tool scores issues, never people.
    contribsutra doctor --root ./workshop-repo
contribsutra plan --root ./workshop-repo --issues issues.json --issue 101 --mode collaborative

    The three plan modes change content, not safety:

    ModeWhat each step containsGood for
    guidedA hintBeginners
    collaborativeA question to discuss with a mentorWorkshops and pairing
    self-directedAcceptance checks onlyExperienced contributors

    Scenario 5: The stale label#

    A help wanted label can sit on an issue for years.

    1. A beginner picks issue #207 because it has the help wanted labelThe snapshot is from this week. The issue was last touched in January 2024.
    2. contribsutra issues --as-of 2026-11-16 marks it staleIt loses 10 points and carries "No activity for 1046 days; confirm the issue is still wanted".
    3. A duplicate #208 appears with the same titleBoth get "Possible duplicate". The contributor asks which one to follow.
    4. She asks before starting. The maintainer says the work was done last yearTen minutes of asking saved a weekend.

    Scenario 6: "All tests pass"#

    Honest evidence is the difference between a review that takes five minutes and one that takes an hour.

    1. A contributor writes "all tests pass" in evidence.jsonContribSutra did not run them.
    2. contribsutra pr-check records the claim as reported_passedVerification is always unverified_external_claim.
    3. The packet separates four channelsVerified: 9 files hashed. User-reported: npm test. Not run: everything else.
    4. The reviewer sees exactly what to checkThe contributor attaches the captured log. Trust is earned, not assumed.

    An evidence.json and the result:

    {"aiAssistance":"assisted","changedFiles":["README.md"],"tests":[{"name":"npm test","status":"passed","evidenceFile":"run.log"}]}
    ChannelItems
    Verified by this tool9 repository files hashed at scan time
    User-reportednpm test: reported_passed
    Inferred / recommendedChecklist items from the project's own policy text
    Not run / unknownTests were not executed by ContribSutra; maintainer intent unknown

    Scenario 7: Someone edits a report#

    A report is easy to change by hand and easy to forge. The seal makes accidental or silent edits visible.

    1. Someone shares a report and edits one finding by handThe JSON still looks fine.
    2. contribsutra verify --report scan.json recomputes the SHA-256 sealIntegrity: MISMATCH. Exit code 1.
    3. contribsutra render refuses to turn it into HTMLNo pretty page hides the edit.
    4. The author regenerates the report from the repositoryHonest output matches the seal again.
    contribsutra verify --report ./reports/scan.json --root ./the-repo
    Note. A SHA-256 seal detects change. It is not a signature and does not prove who wrote the report.

    Scenario 8: An AI assistant in your editor#

    1. A developer installs skills: contribsutra install-skills --ide claude --project .25 folders copied. Nothing overwritten.
    2. Their AI assistant reads contribsutra-prime and calls the real CLIDeterministic output, not a guess.
    3. The assistant reports gaps and drafts questions, then stopsIt cannot open a PR, comment or claim a test passed. Those belong to the human.
    4. The developer decides what to do nextWhether the host activates the skills is not verified. The CLI is what enforces the rules.
    contribsutra install-skills --ide claude --project .

    The hosts and their directories: Claude Code .claude/skills, Cursor .cursor/skills, Codex and OpenCode .agents/skills, Gemini CLI .gemini/skills, GitHub Copilot .github/skills. The command refuses to overwrite and refuses symlinked destinations.

    Scenario 9: A community lead prepares an event#

    1. A community lead prepares a Hacktoberfest-style eventThey want newcomers to succeed and maintainers to stay sane.
    2. They run contribsutra audit --root ./repo --out audit on each participating repositoryOne HTML report per repository, each with findings and a sealed record.
    3. Repositories with MISSING_CONTRIBUTING or no license are fixed firstThe audit lists the important gaps, not a vanity score.
    4. The event starts with repositories at READY_FOR_HUMAN_REVIEWFewer confused newcomers. Fewer unwanted pull requests.
    contribsutra audit --root ./participating-repo --out ./audits/participating-repo

    Each audit is a sealed HTML report the lead can read in a minute. The checklist for a repository to be event-ready: README, CONTRIBUTING, LICENSE present; a "discuss first" or AI-assistance policy stated if you have one; no instruction-like text in the docs.

    What the scenarios have in common#

    1. Nothing is submitted on anyone's behalf.
    2. Every claim has a source, or is marked unknown.
    3. Risky inputs are declined with a reason.
    4. A person always takes the last step.
