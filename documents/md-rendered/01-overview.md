# Overview

> ContribSutra AI helps a first-time open-source contributor become a respectful, capable contributor, and helps maintainers receive fewer, better, more reviewable contributions. Version 0.2.2 is a working, offline command-line tool plus 25 portable agent skills.

## The problem in one picture

Contributing to open source looks simple from outside. In practice a beginner has to answer six questions before writing a line of code, and a maintainer pays the price when they guess wrong.

| Question a beginner asks | What goes wrong without help | What ContribSutra gives |
|---|---|---|
| What is this repository and what does it expect? | Skips `CONTRIBUTING.md`; opens a PR that breaks the rules | A scan with `file:line` sources for policies, license, CI and signals |
| Can my machine run it? | Loses an hour to a wrong Node or Python version | A doctor that compares declared and installed tool versions |
| Which issue is safe and suitable? | Picks a stale, assigned or security-related issue | A ranked shortlist that declines risky issues and says why |
| What is a small first change? | Attempts a huge refactor and gives up | Six small steps with hints and acceptance checks |
| What did I really test? | Writes "tests pass" without running them | A PR packet with unverified claims clearly labelled |
| Am I ready to ask for a review? | Submits a PR nobody asked for | A checklist and a draft description you rewrite yourself |

## How ContribSutra works

{{svg:pipeline}}

Everything inside the dashed zone is read-only and offline. The tool reads files you point it at, reasons with transparent rules, and writes sealed reports outside the repository you inspected. The last step, submitting a pull request, is yours.

## What it will never do

{{svg:trust}}

- It never opens, comments on, assigns, labels or merges anything on GitHub.
- It never runs `npm install`, `make`, `pip` or any script found in a repository, README or issue.
- It never treats issue or README text as instructions. It flags instruction-like text and moves on.
- It never says a test passed because a person, a file or a badge said so.
- It never infers that a maintainer wants a contribution just because an issue is public.

## What you get

| Capability | Command | You receive |
|---|---|---|
| Repository guide | `scan` | Policies, license, toolchain, CI, signals, documented commands, SHA-256 per file |
| Setup doctor | `doctor` | Installed tool versions and whether they satisfy what the repository declares |
| First-win radar | `issues` | A shortlist with reasons, warnings and explicit refusals |
| Learning path | `plan` | Six steps with hints, acceptance checks and human review points |
| PR ProofDesk | `pr-check` | Four evidence channels, a checklist and a draft description |
| Independent audit | `audit` | 30 adversarial checks in HTML, Markdown and JSON |

## Who it is for

- **First-time contributors, students and bootcamp graduates:** know what to do next, and what not to do.
- **Maintainers:** see what newcomers see, and receive fewer unwanted pull requests.
- **Mentors and educators:** run workshops without grading people.
- **Community and developer-relations leads:** audit repositories before an event.
